# 投研资讯刷新反馈与拖拽排序体验设计稿

日期：2026-07-17

## 1. 目标

为 `投研资讯` 页面补齐两个高频交互的即时反馈：

1. 让顶部 `刷新` 按钮在执行过程中具备明确的动态状态，避免像“死按钮”。
2. 让所有可拖拽排序区域在拖动过程中具备稳定、可预期的落点反馈，解决“拖到两个模块中间却放不准”的问题。

本次设计覆盖：

1. `frontend/src/pages/Intel.tsx` 中的顶部 `刷新` 按钮
2. `投研资讯 -> 要点总览` 中五个基本面模块卡片的拖拽排序
3. 当前项目里复用 `SectionTabs` 的所有可拖拽 tab 排序场景

## 2. 非目标

本次不做以下事情：

1. 不引入新的拖拽依赖库
2. 不重写排序持久化逻辑，继续沿用现有 `localStorage` 存储
3. 不改变资讯数据接口、AI 提炼逻辑或模块内容结构
4. 不扩展到当前未使用 `SectionTabs` 的其他自定义拖拽列表

## 3. 问题判断

当前体验存在两个核心问题。

### 3.1 刷新按钮反馈过弱

`投研资讯` 顶部刷新按钮当前只触发 `load()`，缺少以下信息：

1. 用户点击后是否已经开始刷新
2. 当前是否仍在刷新
3. 刷新是否刚刚完成
4. 若接口较慢，页面是否仍然存活

结果就是用户只能看到一个静态按钮，缺乏过程感。

### 3.2 拖拽排序落点不稳定

当前排序实现主要依赖：

1. `dragstart` 记录被拖元素
2. `dragover` 仅标记当前悬停目标
3. `drop` 时将拖动项直接插入到目标项位置

这个模型的问题是：

1. 用户看不到“插到前面还是后面”
2. 当指针停在目标项中间区域时，意图不明确
3. 整块高亮不足以表达最终落点
4. 卡片列表和 tabs 的拖拽反馈不一致，页面手感割裂

## 4. 设计原则

本次交互调整遵循四条原则：

1. 保持轻量：在现有原生拖拽基础上增强，不额外引库
2. 明确落点：拖拽中始终告诉用户会落在目标前还是目标后
3. 状态可见：刷新和拖拽都要让“正在发生什么”可感知
4. 统一语言：卡片和 tabs 使用同一套排序判定与视觉反馈

## 5. 刷新交互设计

### 5.1 状态模型

`投研资讯` 顶部刷新按钮增加三段状态：

1. `idle`
   - 默认状态
   - 按钮文案为 `刷新`
2. `loading`
   - 点击后进入
   - 图标持续旋转
   - 文案切换为 `刷新中...`
   - 按钮禁用，防止重复触发
3. `success-flash`
   - 请求成功后短暂显示
   - 文案切换为 `刚刚更新`
   - 约 1.2 至 2 秒后回到 `idle`

失败时不单独保留长驻状态，直接回到 `idle`，同时继续使用现有 toast 错误提示。

### 5.2 视觉反馈

刷新按钮在 `loading` 期间需要有明显动态变化：

1. `RefreshCw` 图标持续旋转
2. 按钮透明度略降，但仍保持可读
3. 鼠标样式切换为禁用态

请求成功后：

1. 文案显示 `刚刚更新`
2. 可以保留轻微高亮态，表达“刷新完成”

如果后续要继续增强，可再追加“最近刷新时间”，但本次不是必须项。

### 5.3 实现边界

刷新状态仅绑定 `Intel` 页面顶部按钮，不影响其他页面已有刷新逻辑。

`load()` 需要具备以下行为：

1. 开始请求前设置刷新中状态
2. 请求成功后进入完成态
3. 请求失败后回退为空闲态
4. 无论成功失败都确保结束 loading，避免按钮卡死

## 6. 拖拽排序设计

### 6.1 统一判定方式

为卡片列表和 `SectionTabs` 统一采用“前后半区判定”的排序模型：

1. 当指针位于目标元素前半区时，落点为 `before`
2. 当指针位于目标元素后半区时，落点为 `after`

这里的“前后”定义如下：

1. 纵向列表按元素高度中线判断
2. 横向 tabs 按元素宽度中线判断

这样用户拖到两个元素中间时，视觉上会明确看到最终插入位置，而不是只看到目标项整块发亮。

### 6.2 落点状态

拖拽过程中记录一个统一落点信息：

1. `targetKey`
2. `position`
   - `before`
   - `after`

不再只记录“当前悬停的是哪一项”，而是记录“准备插到哪一项的前面还是后面”。

### 6.3 列表卡片反馈

`投研资讯 -> 要点总览` 的五张基本面卡片需要新增以下反馈：

1. 被拖动卡片
   - 半透明
   - 轻微缩放或阴影变化
2. 目标卡片上方或下方
   - 显示一条明确的插入线
   - 或显示一块窄的占位槽
3. 非目标卡片
   - 保持稳定，不整块闪烁

推荐优先使用“插入线 + 边距留白”方案，而不是整个目标卡片描边高亮，因为插入线更接近用户对“排序”的认知。

### 6.4 Tabs 反馈

`SectionTabs` 的横向与纵向场景都采用同一原则：

1. 被拖动 tab 半透明
2. 目标 tab 的前后显示细线或高亮边界
3. 不再只做整颗 pill 或整块 card 高亮

横向 tabs 建议显示左右落点线，纵向 tabs 显示上下落点线。

### 6.5 drop 行为

排序写回逻辑改成基于 `before/after` 计算插入索引：

1. 若落点为 `before`，插入到目标项前面
2. 若落点为 `after`，插入到目标项后面

同时处理一个常见边界：

1. 如果拖动项原本就在目标项前后紧邻位置
2. 重新计算索引时要先移除原项，再按最新目标索引插入

这样可以避免视觉上看似没问题，但最终顺序偏一位的情况。

## 7. 代码结构设计

### 7.1 通用排序工具

建议新增一个轻量级通用工具，专门处理原生拖拽排序中的落点计算与重排。

建议职责：

1. 根据指针位置判断 `before/after`
2. 根据拖动项、目标项和落点计算新的数组顺序

这部分可以放在前端通用工具层，例如：

1. `frontend/src/lib/drag-sort.ts`

该工具不负责 UI，只负责排序判定与数组重排，便于 `Intel.tsx` 和 `SectionTabs.tsx` 共用。

### 7.2 `Intel.tsx` 改造范围

`Intel` 页面需要新增：

1. 顶部刷新状态 state
2. 卡片拖拽中的落点 state
3. 拖动开始、拖动经过、拖动结束、放下时的统一处理

模块顺序持久化方式保持不变，仍写入 `intel-fundamental-module-order`。

### 7.3 `SectionTabs.tsx` 改造范围

`SectionTabs` 需要从当前的：

1. `draggingKey`
2. `dragOverKey`

升级为：

1. `draggingKey`
2. `dropIndicator`
   - 记录目标 key 和前后位置

存储顺序仍使用原有 `draggableStorageKey` 机制，不改数据协议。

## 8. 错误处理与边界条件

需要明确处理以下场景：

1. 拖拽开始后离开可放置区域
   - 清空落点提示
2. 拖拽到自身
   - 不执行排序
3. 找不到拖动项或目标项
   - 安静退出，不写入错误顺序
4. 刷新请求失败
   - 恢复按钮可点击状态
   - 保留现有 toast 错误
5. 页面首次加载与手动刷新并发
   - 以统一的刷新状态为准，避免按钮长时间停在错误态

## 9. 验证标准

验收应至少覆盖以下内容。

### 9.1 刷新反馈

1. 点击 `投研资讯` 顶部刷新按钮后，图标立即旋转
2. 按钮文案切换为 `刷新中...`
3. 刷新成功后短暂显示 `刚刚更新`
4. 刷新失败后按钮恢复为可点击状态

### 9.2 基本面模块排序

1. 拖动卡片到目标卡片上半区时，显示插到前面的落点
2. 拖动卡片到目标卡片下半区时，显示插到后面的落点
3. 放下后顺序与视觉提示一致
4. 刷新页面后模块顺序仍然保留

### 9.3 `SectionTabs` 排序

1. 横向 tabs 拖动时能看到左右落点提示
2. 纵向 tabs 拖动时能看到上下落点提示
3. 放下后顺序与落点提示一致
4. 刷新页面后排序仍然保留

## 10. 接受标准

实现完成后，应满足以下结果：

1. `投研资讯` 顶部刷新按钮具备明确的动态刷新反馈
2. `投研资讯` 五类基本面模块拖拽排序明显更稳，用户能判断前后落点
3. 所有复用 `SectionTabs` 的拖拽排序场景采用统一交互逻辑
4. 不新增第三方依赖
5. 不改动现有排序存储格式与核心业务数据流
