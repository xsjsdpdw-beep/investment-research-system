# 投研资讯仅在有新新闻内容时自动刷新设计稿

日期：2026-07-18

## 1. 目标

为 `投研资讯` 一级页面增加“仅在有新新闻内容时自动刷新”的能力。

核心目标：

1. 用户停留在 `投研资讯` 页面时，系统可以自动感知是否出现了新的新闻内容。
2. 只有当新闻内容真的发生变化时，页面才自动刷新，不因为普通轮询或重复抓取而打扰用户。
3. 自动检测失败时保持页面可用，不弹出强打断式错误，不再出现整页 `HTTP 500`。

## 2. 适用范围

本次仅覆盖：

1. `frontend/src/pages/Intel.tsx`
2. 与 `投研资讯` 刷新流程直接相关的前端辅助逻辑

本次不扩展到：

1. `框架沉淀`
2. `数据库`
3. `日历`
4. 其他一级页面

## 3. 用户意图

用户明确希望：

1. 不要“每次切进来就刷新”
2. 不要“只因为重新抓取过一次就刷新”
3. 只有当出现新的新闻内容时，页面才自动更新

这意味着“自动刷新”的触发标准必须基于内容变化，而不是基于页面进入、轮询成功或缓存时间本身。

## 4. 当前问题

当前 `投研资讯` 页面存在两个不满足用户预期的点：

1. 手动刷新是显式触发的，页面不会在用户停留时自动更新。
2. `radar.generated_at` 只能说明缓存被重新生成过，不能单独证明“新闻内容真的新增或变化”。

因此，如果只以 `generated_at` 变化为条件直接刷新，仍然会出现“看起来刷新了，但其实内容没变”的体验噪音。

## 5. 推荐方案

推荐采用“两阶段检测”的轻轮询方案：

1. 用户停留在 `投研资讯` 一级页面时，启动低频轮询。
2. 每次轮询先读取轻量资讯状态。
3. 只有当轻量状态显示可能有更新时，才继续读取新闻内容并做内容签名比对。
4. 只有签名确实变化时，才自动刷新整个 `Intel` 页面数据。

这是当前项目里最稳、最省改动、最符合用户预期的方案。

## 6. 自动刷新触发规则

### 6.1 何时启用检测

自动检测仅在以下条件同时满足时启用：

1. 当前一级路由为 `/intel`
2. 页面已完成至少一次初始加载
3. 当前不处于手动刷新中

### 6.2 何时停止检测

出现以下任一情况时停止轮询：

1. 用户离开 `/intel`
2. `Intel` 页面卸载
3. 页面正在执行显式手动刷新

### 6.3 轮询频率

推荐采用低频轮询，例如：

1. 每 60 秒检查一次

本次不需要做用户可配置项，先固定一个稳妥值即可。

## 7. “有新内容”的判断标准

### 7.1 第一阶段：轻量变化检测

第一阶段读取一个轻量状态，建议复用已有 `radar` 数据中的：

1. `generated_at`

它的作用不是直接触发页面刷新，而是作为“是否值得进一步比对”的门槛。

判断规则：

1. 如果 `generated_at` 未变化，直接跳过本轮，不刷新页面。
2. 如果 `generated_at` 变化，再进入第二阶段。

### 7.2 第二阶段：新闻内容签名比对

第二阶段需要对“会展示给用户的新闻内容”生成一个稳定签名，并与当前页面已知签名比较。

建议签名范围：

1. `global_tech_headlines`
2. `macro_events`
3. `industry_dynamics`
4. `stock_topics`
5. `stock_dynamics`
6. `geopolitics.items`

建议只取这些结构中真正代表新闻条目的关键字段，例如：

1. `title`
2. `url`
3. `time`
4. `source`

必要时可包含模块 key 或 industry key，避免不同模块同标题时碰撞。

### 7.3 最终判定

只有在以下条件同时成立时，才执行自动刷新：

1. `generated_at` 变化
2. 新内容签名与当前页面缓存签名不同

这可以避免“后台重新抓了一次但内容完全相同”时页面白刷新。

## 8. 自动刷新后的页面行为

自动刷新命中后：

1. 重新执行 `Intel` 现有的数据加载流程
2. 更新新闻内容
3. 更新“资讯更新于 ...”时间
4. 更新内部内容签名缓存

自动刷新是静默完成的，不需要弹出成功 toast。

可接受的轻提示：

1. 顶部时间变化
2. 可选的轻微状态闪烁

本次优先保持安静，不额外加提示条。

## 9. 错误处理

### 9.1 轮询失败

轮询失败时：

1. 保持当前页面内容不动
2. 本轮静默结束
3. 下一个周期继续尝试

不弹错误 toast，避免用户停留页面时被周期性报错骚扰。

### 9.2 刷新接口失败

若进入第二阶段后自动刷新失败：

1. 延续当前已有策略
2. 优先回退到最近缓存
3. 页面继续可用

### 9.3 并发保护

需要避免以下冲突：

1. 手动刷新与自动检测同时触发
2. 连续两个轮询周期重叠

因此应增加前端级别的“检测中/刷新中”保护，确保同一时间只跑一个自动检测流程。

## 10. 代码结构建议

### 10.1 新增轻量内容签名工具

建议把内容签名逻辑抽到单独工具文件，保持 `Intel.tsx` 不继续膨胀。

推荐职责：

1. 从 `ResearchHubData` 中提取新闻内容关键字段
2. 生成稳定字符串或哈希签名

### 10.2 `Intel.tsx` 职责

`Intel.tsx` 负责：

1. 页面挂载时完成初始加载
2. 维护当前 `radar.generated_at`
3. 维护当前内容签名
4. 在 `/intel` 停留期间启动和清理轮询
5. 在检测到新内容时触发静默自动刷新

### 10.3 现有刷新逻辑复用

自动刷新应尽量复用现有 `load()` 或其底层 helper，而不是另写第二套页面更新逻辑。

原则：

1. 手动刷新和自动刷新共享同一份数据装载逻辑
2. 只在触发条件、提示方式和错误处理上区分

## 11. 验证标准

至少覆盖以下场景：

### 11.1 无更新

1. 停留在 `/intel`
2. 轮询命中，但 `generated_at` 未变化
3. 页面不刷新

### 11.2 仅时间变化、内容不变

1. `generated_at` 变化
2. 内容签名不变
3. 页面不自动刷新

### 11.3 内容真正变化

1. `generated_at` 变化
2. 内容签名变化
3. 页面自动刷新
4. “资讯更新于 ...”同步更新

### 11.4 自动检测失败

1. 轮询接口失败
2. 页面继续显示当前内容
3. 不弹周期性错误提示

### 11.5 离开页面

1. 从 `/intel` 跳转到其他一级页面
2. 轮询停止
3. 不继续发检测请求

## 12. 接受标准

完成后应满足：

1. 用户停留在 `投研资讯` 一级页面时，系统会自动检测新闻是否有更新。
2. 只有出现新的新闻内容时，页面才自动刷新。
3. 仅 `generated_at` 变化但内容不变时，页面不刷新。
4. 自动检测失败不会打断用户当前页面。
5. 自动检测只在 `/intel` 一级页面停留期间运行。
