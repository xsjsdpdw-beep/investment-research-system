# 投研资讯事件概率一级看板骨架设计稿

日期：2026-07-17

## 1. 目标

在 `投研资讯` 中新增一个与 `基本面`、`流动性` 并列的一级情报轴：`事件概率`。

本次只落骨架，不承诺真实概率数据接入。目标是先把信息架构、页面状态、后端数据协议、占位模块和测试支撑接好，让后续把真正的“事件概率体系”接进来时不需要再改一次导航和页面分层。

本次设计覆盖：

1. `frontend/src/lib/workspace.ts` 中 `投研资讯` 的子导航与 `INTEL_TABS`
2. `frontend/src/pages/Intel.tsx` 中一级 tab、二级视图和占位模块
3. `frontend/src/lib/api.ts` 中 `ResearchHubData` 对应的数据类型
4. `backend/research_hub.py` 中 `get_research_hub()` 返回结构
5. 与上述结构绑定的测试断言

## 2. 非目标

本次不做以下事情：

1. 不接入真实的事件概率数据源
2. 不实现概率计算、赔率换算、情景打分或胜率模型
3. 不引入新的外部依赖或新的数据库
4. 不修改现有 `基本面` 和 `流动性` 的内容逻辑
5. 不把“事件概率”伪装成已经生产可用的数据模块

## 3. 背景与问题判断

当前 `投研资讯` 已经形成了一个双主轴结构：

1. `基本面`
2. `流动性`

这套结构已经同时体现在：

1. 左侧导航子项
2. `INTEL_TABS`
3. `Intel` 页面一级状态切换
4. `research_hub` 返回结构
5. 测试断言

因此用户提出“把这套体系接到投资资讯下面的二级看板中去，就用事件概率命名，与基本面、流动性并列在一起”，本质上不是“多一张卡片”，而是给 `投研资讯` 新增第三个一级情报轴。

如果继续把内容塞进 `基本面` 或某个现有卡片下面，会出现两个问题：

1. 信息架构不符合用户对“并列一级”的要求
2. 后续真接概率体系时还要再做一次结构迁移

因此本次应优先建立第三栏骨架。

## 4. 设计原则

本次调整遵循以下原则：

1. 结构先行：先把入口和承载面放对，再接真实内容
2. 命名直接：统一使用 `事件概率`，不做更抽象的替代名称
3. 明示占位：页面要清楚告诉用户哪些已经是骨架、哪些尚待接入
4. 最小侵入：只改 `投研资讯` 相关结构，不牵动其他主模块
5. 可扩展：后续接入真实概率源时，尽量不需要再改导航、tab key 和数据协议

## 5. 信息架构设计

### 5.1 一级结构

`投研资讯` 从当前的两项扩展为三项：

1. `基本面`
2. `流动性`
3. `事件概率`

该结构需要在以下两个入口保持一致：

1. 左侧导航 `children`
2. `INTEL_TABS`

对应前端 key 建议统一使用 `event-probability`，以保持与现有 kebab-case 风格一致，避免和后端 snake_case 直接耦合。

### 5.2 二级视图结构

`事件概率` 一级看板下，本次先提供三个二级视图：

1. `总览`
2. `重点事件`
3. `数据接口`

这样可以避免用户点进去后只看到单段空文案，也为后续真实体系预留自然落点。

建议的 key：

1. `overview`
2. `priority-events`
3. `sources`

### 5.3 与现有两栏的关系

`基本面`、`流动性` 现有视图结构不改。

`事件概率` 是新增并列层，不复用 `基本面` 的模块排序 key，也不插入 `流动性` 的内容区。三栏并列、三套状态独立。

## 6. 页面骨架设计

### 6.1 总览视图

`总览` 是用户进入 `事件概率` 后的默认视图，承担三个任务：

1. 说明这是什么
2. 说明当前做到哪一层
3. 说明后续会承接哪些事件概率模块

建议包含以下内容块：

1. 顶部说明卡
   - 标题：`事件概率体系入口`
   - 说明：当前先接骨架，后续承接真实事件概率源、自建情景判断和重点催化库
2. 模块总览卡
   - 用 3 张小卡片展示未来重点模块方向
3. 下一步提示卡
   - 说明接真实数据时优先接哪几类源

### 6.2 重点事件视图

`重点事件` 先展示一组后端返回的占位事件卡，而不是空列表。

每条事件建议至少包含：

1. `title`
2. `category`
3. `status`
4. `note`

这些字段本次只做展示，不做概率值计算。用途是先把未来真实“事件清单”的列表结构定下来。

建议页面语义更偏“观察清单”，例如：

1. 海内外重要政策窗口
2. 核心行业催化时点
3. 用户后续重点跟踪的事件模板

### 6.3 数据接口视图

`数据接口` 用来说明当前与未来的数据承载点，避免用户误以为数据已经接好。

建议展示三类来源：

1. 已接骨架接口
   - 当前 `research_hub` 节点
2. 公开数据源占位
   - 例如公开宏观日历、政策窗口、会议日历
3. 后续高级接口占位
   - 例如事件数据库、情景概率表、自建判断模块

每条来源建议包含：

1. `label`
2. `provider`
3. `status`
4. `note`

## 7. 后端数据协议设计

### 7.1 `research_hub` 新增节点

`backend/research_hub.py` 的 `get_research_hub()` 新增 `event_probability` 节点，与 `fundamental`、`liquidity` 同级。

建议结构：

```python
"event_probability": {
    "summary": {
        "title": "事件概率体系入口",
        "description": "...",
        "updated_at": "..."
    },
    "planned_modules": [...],
    "priority_events": [...],
    "source_interfaces": [...]
}
```

### 7.2 字段说明

`summary`

1. 用于 `总览` 视图顶部说明
2. 明确当前是骨架态

`planned_modules`

1. 用于展示未来模块方向
2. 本次建议至少返回 3 项，避免页面空洞

每项建议包含：

1. `key`
2. `label`
3. `description`
4. `status`

`priority_events`

1. 用于 `重点事件` 视图
2. 返回占位观察对象

每项建议包含：

1. `key`
2. `title`
3. `category`
4. `status`
5. `note`

`source_interfaces`

1. 用于 `数据接口` 视图
2. 既能承载当前接口，也能承载未来扩展源

每项建议包含：

1. `key`
2. `label`
3. `provider`
4. `status`
5. `note`

### 7.3 数据来源策略

本次所有 `event_probability` 数据都由后端本地静态生成，不依赖新外部调用。

原因：

1. 用户这次明确选择先接骨架
2. 先把协议和前端消费路径做稳定
3. 避免引入半成品数据后再返工字段设计

## 8. 前端状态与交互设计

### 8.1 一级 tab 状态

`Intel` 页面现有 `active` 状态支持 `fundamental` 与 `liquidity`，本次扩展为支持 `event-probability`。

默认行为保持不变：

1. 未指定 query 参数时仍进入默认一级页
2. 若 query 参数命中 `event-probability`，可直接进入该看板

### 8.2 二级视图状态

新增独立状态，例如：

1. `eventProbabilityView`

其可选值：

1. `overview`
2. `priority-events`
3. `sources`

该状态与 `fundamentalView`、`liquidityView` 完全独立，避免互相污染。

### 8.3 排序与持久化

为了与现有交互习惯保持一致，`事件概率` 也应支持自己的二级视图拖拽排序。

新增独立持久化 key：

1. `intel-event-probability-view-order`

本次不为 `事件概率` 总览卡片额外设计模块拖拽排序；只要求二级视图 tab 顺序可以与现有 `SectionTabs` 机制一致地持久化。

### 8.4 占位态表达

前端文案需要明确：

1. 当前已接入的是结构化入口
2. 不是实时概率引擎
3. 后续可继续挂接真实模块

禁止出现容易让人误读为“当前概率已经算好”的文案，例如：

1. `当前胜率`
2. `模型判断`
3. `市场隐含概率`

除非未来真实数据接入后再另行设计。

## 9. API 类型设计

`frontend/src/lib/api.ts` 中 `ResearchHubData` 需要新增 `event_probability` 类型描述。

要求：

1. 字段名与后端返回结构一致
2. 不使用过宽的 `any`
3. 与 `Intel.tsx` 中消费字段一一对应

建议为以下对象定义显式类型：

1. `EventProbabilitySummary`
2. `EventProbabilityModule`
3. `EventProbabilityItem`
4. `EventProbabilitySource`

## 10. 测试设计

### 10.1 后端接口测试

更新 `backend/tests/test_workspace_api.py`：

1. `GET /api/research/hub` 返回数据中包含 `event_probability`
2. `event_probability.summary.title` 存在
3. `event_probability.priority_events` 至少有 1 项
4. `event_probability.source_interfaces` 至少有 1 项

### 10.2 前端结构测试

更新 `tests/test_branding_acceptance.py`：

1. `workspace.ts` 中 `投研资讯` 子项包含 `事件概率`
2. `INTEL_TABS` 包含 `事件概率`
3. `Intel.tsx` 包含 `draggableStorageKey="intel-event-probability-view-order"`

### 10.3 验收标准

至少满足以下结果：

1. 左侧导航进入 `投研资讯` 后可见 `基本面 / 流动性 / 事件概率`
2. `事件概率` 能作为一级 tab 独立切换
3. 进入 `事件概率` 后能看到 `总览 / 重点事件 / 数据接口`
4. 页面不依赖外部新数据源也能完整渲染
5. `research_hub` 返回结构已能承载后续真实接入

## 11. 风险与边界

### 11.1 命名一致性

前端建议用 `event-probability`，后端建议用 `event_probability`。实现时要注意两端映射清晰，不要混用导致条件分支失效。

### 11.2 用户误解风险

如果占位文案不够明确，用户可能误以为这是一个已经接好真实概率数据的模块。因此页面 copy 必须持续强调“骨架入口”和“后续接入”。

### 11.3 范围膨胀风险

本次很容易被带成“顺手把真实事件概率也接了”。需要明确克制，只做骨架，不在本次顺手加入真实数据抓取、概率算法或复杂配置。

## 12. 实施切分建议

实现可以按以下顺序进行：

1. 先扩 `workspace.ts` 与 `INTEL_TABS`
2. 再扩 `research_hub.py` 与 `api.ts` 类型
3. 然后改 `Intel.tsx` 的一级/二级视图状态和渲染
4. 最后补测试断言

这样可以把结构变更控制在最少的文件集里，也方便逐步验证。

## 13. 成功标准

本次完成后，`投研资讯` 将从“双栏结构”升级为“三栏结构”：

1. `基本面`
2. `流动性`
3. `事件概率`

其中 `事件概率` 已具备：

1. 明确的一级入口
2. 独立的二级视图
3. 稳定的前后端数据协议
4. 可继续承接真实事件概率体系的页面骨架

但仍明确保持：

1. 不输出真实概率值
2. 不伪装成已完成的数据产品
3. 不改变现有两栏的行为
