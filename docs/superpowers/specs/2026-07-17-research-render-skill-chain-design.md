# 投研资料统一摄取与美化 Skill 底座设计

日期：2026-07-17

## 1. 背景

当前行业概览、个股概览已经具备：

- 有道云主笔记绑定与同步
- 附件投喂入口
- 初稿 / 深度 / 待吸收三段式工作流
- 候选池与人工确认替换机制

但目前“提取后展示”的核心问题仍然存在：

- `.note` / 研报正文进入系统后，多数仍表现为长段文字
- 前端主要在做“文本后处理”，而不是“结构化内容渲染”
- 产业链、流程图、对比表、关键指标拆解等内容缺少合适的视觉表达
- 初稿与深度虽然已有不同职责，但底层内容结构不统一，后续难以持续进化

用户希望把这些能力整合成自己的一套本地 skill 底座：

- `MinerU`：负责 PDF / Office / 图片等资料的结构化提取
- `PaddleOCR`：负责图片、截图、扫描文档的主 OCR 与版面理解
- `OCRmyPDF`：负责扫描 PDF 的 OCR 预处理与可搜索文本层增强
- `Umi-OCR`：负责本地图片类材料与复杂截图场景的 OCR 兜底
- `markdown-viewer/skills`：负责将结构化信息表达为图表、流程图、信息卡、信息图等块级视觉组件
- `Kami`：负责整体页面的文档气质、排版节奏、表格风格、图注与来源区
- `CyberPPT`：负责高信息密度、咨询风格、证据链驱动的页面组织与版式约束

目标不是直接照搬第三方项目，而是把它们的长处落到当前投研系统中，形成一条：

`有道云笔记 / 本地 PDF / 研报 -> 结构化提取 -> 候选版本 -> 美化预览 -> 人工确认替换`

的可控链路。

## 2. 本期目标

本期只打通两类高价值输入：

1. 有道云笔记
2. 本地 PDF / 研报文件

并且只先服务两个场景：

1. 行业概览
2. 个股概览

同时把以下链路一次打通：

1. 附件投喂入口
2. 结构化提取
3. 候选池
4. 概览预览渲染
5. 人工确认替换

## 3. 不做什么

本期不做：

- 全量网页 / 公众号 / 图片网页抓取统一接入
- 自动直接覆盖深度内容
- 对深度主编辑器做全面重写
- 所有页面统一替换为这套渲染链
- 自动生成固定图片海报作为主交付物

这些能力可以作为第二期或后续增量。

## 4. 三层架构

### 4.1 输入层

输入层沿用现有入口，但一期只真正打通：

- `有道云笔记导入`
- `上传 PDF / 研报文件`

其中：

- 有道笔记适合作为长期沉淀、纪要、电话会、专家会、框架类资料的来源
- PDF / 研报适合作为正式研究材料、图表、行业流程、估值表和结构化表格的来源

现有“粘贴链接”入口继续保留，但本期只把它视为附件记录，不纳入主提取链。

### 4.2 提取层

新增统一的本地摄取与美化底座：`research_ingest_skill`

建议以 backend 本地模块形式落地，先不单独拆微服务。

核心子模块：

- `SourceAdapters`
- `OcrExtractRouter`
- `YoudaoExtractor`
- `PdfExtractor`
- `ImageExtractor`
- `RenderNormalizer`
- `CandidateBuilder`
- `RenderPack`

职责如下：

#### `SourceAdapters`

输入：

- 有道云笔记
- 本地 PDF / 研报
- 单独上传图片
- 现有附件投喂记录

输出：

- 标准化源对象
- 文件路径 / file_id / 来源标题 / 来源类型

说明：

这层的目标是让前台永远只有“投喂资料”这一种动作，而不是让用户自己选择走哪种工具链。

#### `OcrExtractRouter`

输入：

- 标准化源对象

输出：

- 选定的提取链路
- OCR / 提取中间结果

路由规则一期固定为：

- 电子 PDF：优先 `MinerU`
- 扫描 PDF：`OCRmyPDF -> PaddleOCR`
- 有道纯正文：直接正文提取，不走 OCR
- 有道中的图片 / 截图：优先 `PaddleOCR`，复杂场景用 `Umi-OCR` 兜底
- 单独上传图片：优先 `PaddleOCR`，必要时回退 `Umi-OCR`

说明：

这层对外不可见，只作为 skill 内部自动路由逻辑存在。

#### `YoudaoExtractor`

输入：

- noteId / fileId
- 有道正文内容
- 有道关联图片或基础元信息

输出：

- 原始文本块
- 标题层级
- 列表、表格、引用、图片引用
- 来源元信息

说明：

有道笔记本质上更像富文本源，提取时需要优先保留：

- 标题结构
- 段落边界
- 图片位置
- 表格语义
- 链接与来源说明

#### `PdfExtractor`

输入：

- 本地 PDF / 研报文件

输出：

- MinerU 产出的 Markdown / JSON
- 表格 HTML / Markdown
- 图片区域、图注、页码、标题

说明：

这里不把 PDF 处理只绑定在一种工具上，而是由 `OcrExtractRouter` 先判断：

- 电子 PDF：封装 MinerU 的结果
- 扫描 PDF：先 OCRmyPDF，再交给 PaddleOCR 或后续结构化转换

第一期可以采用：

- 本地 CLI 调用
- 或本地 Python 包调用

优先要求是“可在本机稳定运行”，不是追求一次性支持所有格式。

#### `ImageExtractor`

输入：

- 单张图片
- 多张图片
- 有道笔记正文中的图片引用

输出：

- OCR 文本
- 版面块
- 表格 / 流程 / 说明区域的结构化结果

说明：

这层优先使用 `PaddleOCR`，在页眉页脚、水印、截图噪声较重或批量图片场景下允许回退 `Umi-OCR`。

#### `RenderNormalizer`

这是整条链路的核心。

它要把上游不同来源统一转成系统内部的“结构块”。

内部结构建议定义为：

- `section`
- `paragraph`
- `bullet_list`
- `quote`
- `table`
- `metric_grid`
- `timeline`
- `process_flow`
- `industry_chain`
- `comparison_cards`
- `image`
- `chart_spec`
- `source_ref`

这个结构是系统真值，不再让前端直接猜 Markdown 文本。

#### `CandidateBuilder`

职责：

- 从结构块中识别可更新章节
- 生成候选版本
- 生成候选摘要
- 记录替换建议
- 保留与原版本的对比信息

输出对象至少包含：

- `candidate_id`
- `scope_type`
- `scope_id`
- `target_section_key`
- `source_type`
- `source_title`
- `summary`
- `structured_blocks`
- `render_recipe`
- `diff_preview`
- `status`

## 5. 渲染层设计

### 5.1 基本原则

系统预览页不再以“纯 Markdown 文本渲染”为中心，而是以“结构块渲染”为中心。

也就是说：

- 文本只是块的一种
- 表格不再只显示成原生表格
- 短流程不再只显示为列表
- 产业链不再只是一段描述

### 5.2 两层渲染

#### 第一层：文档骨架

参考 Kami 与 CyberPPT 的思路，定义系统内统一的“投研文档骨架”：

- 统一标题层级
- 稳定留白
- 稳定行距
- 统一图注
- 统一来源区
- 表格与卡片的统一底色、边框、阴影风格
- 高信息密度页面中的证据分组、页内层级和信息主次组织
- 适合咨询式研究页面的摘要栏、要点区、证据区、结论区分层

这层决定“整页气质”，目标是让页面更像可读的研究文档，而不是仪表盘或笔记拼接。

其中：

- `Kami` 更偏“文档气质、纸面阅读感、统一视觉约束”
- `CyberPPT` 更偏“高密度咨询风、证据链、SCR 组织、页面蓝图”

系统内并不直接生成 PPT，而是吸收它的“高密度页面如何组织”的方法。

#### 第二层：块级视觉表达

参考 markdown-viewer/skills 的思路，为不同结构块映射到不同组件：

- `table` -> 美化表格 / 条形对比表
- `metric_grid` -> 指标卡组
- `timeline` -> 时间线
- `process_flow` -> 流程步骤图
- `industry_chain` -> 横向产业链图 / 节点图
- `comparison_cards` -> 竞品对比卡片
- `chart_spec` -> Vega / 自定义图表

重点不是全量照搬 markdown-viewer，而是吸收它“按内容类型选视觉模板”的方法。

### 5.2.1 OCR 结果统一输出

无论走哪条 OCR / 提取链，最终都只允许输出为同一套 `StructuredRenderBlock[]`。

同时为后续候选替换保留附加信息：

- `origin_type`
- `origin_page`
- `origin_bbox`
- `ocr_engine`
- `confidence`

这样前台看到的是统一结构，后台仍然能追溯“这段是正文提取的，还是 OCR 识别出来的”。

### 5.3 初稿与深度统一壳

本期要求：

- 初稿和深度都统一成 `左侧目录 + 右侧内容` 的阅读骨架
- 两者底层都消费同一套 `structured_blocks`

区别只在于：

- 初稿：自动候选更多、自动内容更强
- 深度：以你已确认的版本为主，只接收候选替换

### 5.4 高密度研究页规则

为避免概览页继续变成“有标题的长文”，本期新增一套高密度研究页规则，吸收 CyberPPT 的方法，但输出仍然是系统内页面，而不是 PPT：

- 单个章节优先拆成 `结论 / 证据 / 图表 / 备注` 四段式，而不是只给一整段正文
- 当章节存在多来源证据时，优先展示“证据卡组”或“对比表”，而不是简单拼接来源文本
- 当同一章节包含数字、对比、判断、风险时，按 SCR 或“先结论后证据”方式组织顺序
- 允许行业概览、个股概览在局部呈现“准咨询页”形态，例如：页头结论条、主体证据板、下方 caveat / 来源条

这套规则主要服务：

- 行业概览的市场规模、产业链、竞争格局、关键指标章节
- 个股概览的公司定位、业务拆解、核心产品、盈利模式、风险提示章节
- 后续导出报告与学习工坊摘要板

## 6. 候选替换机制

用户已明确：

- 不允许自动覆盖
- 一律先生成候选版本，再人工确认替换

因此流程固定为：

1. 新资料进入系统
2. 提取结构块
3. 匹配到行业 / 个股概览中的某个章节
4. 生成候选摘要与候选可视化结果
5. 在候选池展示“当前版本 vs 候选版本”
6. 用户确认后替换
7. 记录留痕

### 6.1 替换单位

替换不以整篇概览为单位，而以“章节”为单位。

建议引入稳定章节键：

- `market-size-demand`
- `industry-chain`
- `competitive-landscape`
- `core-process`
- `key-players`
- `financial-profile`
- `key-risks`

行业、个股可以有不同默认章节模板，但都要用稳定 key 管理。

### 6.2 留痕

每次候选确认后都记录：

- 替换前内容摘要
- 替换后内容摘要
- 来源
- 时间
- 处理人

深度页中保留最近版本留痕入口。

## 7. 数据模型变更

### 7.1 新增结构块模型

建议在前后端统一新增：

`StructuredRenderBlock`

字段示意：

- `id`
- `type`
- `title`
- `section_key`
- `content`
- `items`
- `table`
- `image`
- `chart_spec`
- `source_refs`
- `children`
- `render_hint`

### 7.2 新增概览渲染包

在 `overview_workbench` 记录中新增：

- `draft_structured_blocks`
- `deep_structured_blocks`
- `render_candidates`
- `render_theme`

原有 Markdown / body 字段不立即删除，先作为兼容层保留。

## 8. 页面改造

### 8.1 附件投喂入口

在行业中心 / 个股中心的“附件投喂”模块中：

- 有道云笔记导入成功后，直接进入候选生成链
- PDF 上传成功后，直接进入候选生成链

UI 上要明确显示：

- 已导入
- 提取中
- 已生成候选
- 可预览

### 8.2 初稿页

初稿页改为：

- 左侧目录
- 右侧结构化渲染预览
- 底部展示最近更新研报
- 保留信息源区

但正文主体不再以纯文本块为主。

### 8.3 深度页

深度页改为：

- 左侧目录
- 右侧主内容
- 候选替换入口
- 留痕入口

深度中不直接编辑块本体，而是通过候选替换和有道主笔记同步维持。

## 9. Skill 形态

这次不把第三方仓库分散接入，而是统一收成你自己的一个本地 skill 底座：`research_ingest_skill`。

对外它只暴露一套能力：

- 导入有道云笔记
- 上传 PDF / 研报 / 图片
- 生成候选版本
- 预览美化结果
- 确认替换到初稿 / 深度

内部再分成两类能力：

### 9.1 运行时能力

放在当前系统 backend 内：

- 源适配
- OCR / 提取路由
- MinerU 调用封装
- OCRmyPDF 调用封装
- PaddleOCR 调用封装
- Umi-OCR 调用封装
- 结构块归一化
- 候选版本生成

### 9.2 设计资产能力

吸收 markdown-viewer/skills、Kami 与 CyberPPT 的方法，形成：

- 一套概览块级渲染模板
- 一套页面排版主题
- 一套流程图 / 产业链图 / 表格图的映射规则
- 一套高信息密度研究页的布局规则
- 一套“结论 - 证据 - 图表 - caveat”页面构成规则

后续如果需要，再把这整套抽成你自己的本地 skill。

### 9.3 四者分工

为避免后续实现时边界混乱，四者分工固定如下：

- `MinerU`：电子 PDF / 文档的主提取
- `OCRmyPDF`：扫描 PDF 预处理
- `PaddleOCR`：图片、截图、扫描文档的主 OCR
- `Umi-OCR`：图片资料与复杂截图兜底 OCR
- `markdown-viewer/skills`：块级图形表达
- `Kami`：整体阅读气质与文档视觉
- `CyberPPT`：高密度研究页组织、咨询风版式语言、证据链页面结构

## 10. 实施顺序

建议按四步走：

### Step 1

先打通 `统一源适配 + OCR / 提取路由`

验证目标：

- 能自动区分电子 PDF、扫描 PDF、有道正文、有道图片、单独图片
- 能为每类资料选中正确工具链

### Step 2

打通 `PDF / 图片 / 有道 -> Structured Blocks`

验证目标：

- 一篇典型研报能提取出标题、段落、表格、图片、图注
- `.note / md` 类型笔记都能保留基本层级、空行、图片、列表结构
- 单张图片和截图能进入统一结构块

### Step 3

落地概览渲染器 V2

验证目标：

- 初稿与深度都能消费 `StructuredRenderBlock[]`
- 至少支持：段落、表格、流程块、时间线、图片、来源区

### Step 4

打通候选池替换链路

验证目标：

- 附件投喂后可以生成候选
- 候选可预览
- 确认后替换到目标章节
- 记录留痕

## 11. 风险与规避

### 风险 1：OCR / 提取链路依赖较重

规避：

- OCR 与提取统一走本地适配器
- 先做 CLI 适配
- 如本机环境不稳定，增加“回退到纯文本抽取 / 单引擎 OCR”降级路径

### 风险 2：有道 `.note` 与图片混合结构不稳定

规避：

- 先把有道作为正文源
- 图片和截图单独走 OCR 适配器
- 富文本细节逐步增强
- 中间结构层永远允许回退为 `paragraph + image + source_ref`

### 风险 3：视觉模板过多导致复杂度失控

规避：

- 一期只落地 5 类高频组件：
  - `paragraph`
  - `table`
  - `process_flow`
  - `timeline`
  - `industry_chain`

### 风险 4：误替换深度内容

规避：

- 严格候选替换制
- 不允许自动覆盖
- 替换单位固定为章节

## 12. 验收标准

满足以下条件即可视为一期完成：

1. 你上传一篇本地 PDF 研报，系统能提取结构并生成候选
2. 你导入一篇有道云笔记，系统能提取结构并生成候选
3. 初稿页不再只是纯文字，而能显示更好的表格 / 流程 / 图文混排结果
4. 深度页也采用同一套目录加正文骨架
5. 替换前必须可预览候选内容
6. 确认替换后可保留版本留痕

## 13. 推荐落地结论

推荐按本设计执行。

原因：

- 它正对当前最痛的问题：资料进来了，但长得不像可读的研究页面
- 它保留了你已经建立好的“有道主笔记 + 候选池 + 深度沉淀”工作流
- 它把源适配、OCR、提取、排版、美化分层，后续接 AlphaEngine、专家纪要、数据库自动图表时不需要推翻重做
- 它额外吸收了 CyberPPT 的高密度咨询风组织方法，能让概览页更接近真正可读、可扫、可复盘的研究页面，而不是“更好看的长文”

本质上，这不是“给 Markdown 加点样式”，而是把你的投研资料流升级成：

`可提取、可结构化、可候选、可替换、可留痕`

的一条长期底座。
