# Vibe-Research 接入设计

## 背景

当前工作目录 `/Users/leo/Documents/投研体系` 为空目录。目标不是零散借用 `Vibe-Research` 的单个模块，而是以它作为底座，在当前目录搭建一套属于用户自己的投研体系版本。

上游项目 `Vibe-Research` 是完整的双端应用，而不是单独组件库。根据上游 README，它包含：

- `backend/`：FastAPI 服务，默认端口 `8900`
- `frontend/`：React 19 + Vite + TypeScript，默认端口 `5899`
- `a-stock-data/`：A 股数据工具箱
- `global-stock-data/`：美股 / 港股数据工具箱
- 本地存储、自选、持仓、研报、研究记录、AI 接入等完整能力

因此，第一阶段最稳妥的路径是：先完整引入并跑通上游项目，再逐步改造成用户自己的版本。

## 目标

第一阶段只完成“底座接入成功”，不把“系统跑通”和“业务定制”混成一个阶段。

具体目标：

1. 当前目录成为一个可运行的 `Vibe-Research` 衍生项目根目录。
2. 保持上游原始目录结构，避免在首次接入时做架构级改造。
3. 按上游默认方式启动前后端，验证本地可运行。
4. 为第二阶段的品牌、配置和投研流程改造保留清晰边界。

## 非目标

第一阶段不做以下事项：

- 不重构前后端架构
- 不提前删除页面或模块
- 不替换上游数据抓取底层
- 不一开始就改造成完全定制版投研流程
- 不在接入阶段做大规模 UI 改版
- 不把本次“接入”与后续“自动化工作流”绑定在一起

## 方案选择

针对空目录接入上游完整项目，有三种典型做法：

### 方案 A：直接以当前目录作为上游项目根目录

做法：

- 将 `Vibe-Research` 的完整内容落到当前目录
- 当前目录直接成为用户自己的项目根目录
- 先按上游 README 启动并验证

优点：

- 最快跑通
- 最容易对照上游文档与代码排错
- 后续改造成本最低
- 符合“先完整拉起，再逐步改成自己的版本”的目标

缺点：

- 第一版会保留上游命名、默认文案和部分默认配置

### 方案 B：上游代码放入子目录，外层再包一层用户项目

做法：

- 在当前目录下建立单独子目录承载上游代码
- 外层再新增自定义脚本、配置或包装层

优点：

- 上游与用户自定义边界表面上更清晰

缺点：

- 启动路径和依赖管理更绕
- 第一阶段排错复杂度上升
- 不利于“先跑起来”

### 方案 C：手工挑选上游文件迁入空目录

做法：

- 不完整引入仓库，只迁入认为“需要”的目录或文件

优点：

- 看起来更轻

缺点：

- 最容易漏依赖、漏配置、漏静态资源
- 首次接入失败概率最高
- 与用户的目标不一致

## 最终方案

采用方案 A：直接以当前目录作为 `Vibe-Research` 衍生项目根目录。

原因：

- 当前目录为空，最适合完整落地上游结构
- 用户已经明确选择“先完整拉起，本地可运行，再逐步改成自己的版本”
- 上游本身已提供完整前后端、数据层和 AI 接口，接入阶段不应额外引入结构复杂度

## 第一阶段实施设计

### 1. 目录落地

第一阶段尽量保持上游结构不动，目标目录应与上游主结构保持一致：

- `frontend/`
- `backend/`
- `a-stock-data/`
- `global-stock-data/`
- 根目录说明文档、依赖文件、截图与配置文件

这保证了后续遇到任何启动或依赖问题时，都能直接对照上游 README 与源码定位。

### 2. 启动方式

第一阶段按上游默认方式运行，不主动改端口、不改脚本入口：

- 后端：`backend/` 中创建虚拟环境、安装依赖，并以 `uvicorn app:app --host 127.0.0.1 --port 8900` 启动
- 前端：`frontend/` 中安装依赖并以开发模式启动，默认访问 `http://localhost:5899`

这样验证的是“上游项目在当前机器是否完整可运行”，而不是“被改过之后是否还能运行”。

### 3. 配置边界

第一阶段不主动改业务逻辑，但要提前识别第二阶段必然会改的配置点，后续优先做配置收口。重点关注：

- 项目名称、导航文案、首页说明
- AI 接入默认项和相关配置
- 本地数据保存路径
- 自选、持仓、研究记录、研报目录
- 服务地址和环境变量命名

这些内容先记录、后收口，不在第一阶段混入功能改造。

### 4. 验收标准

第一阶段完成的判断标准不是“已经完全变成用户的投研体系”，而是“底座接入成功并可运行”。验收标准如下：

1. 后端能够本地启动
2. 前端能够本地启动并访问
3. 首页与核心导航能够正常加载
4. AI 接入页面能够打开
5. 本地型功能如自选、持仓、研究记录至少具备基础可用性

只要满足以上标准，就视为第一阶段成功。

## 第二阶段改造优先级

在底座跑通后，第二阶段优先改造以下内容：

### 1. 品牌与入口

优先将项目名、首页文案、导航命名、默认说明改成“投研体系”语境。这类改动用户感知最强，风险最低。

### 2. 配置收口

将散落的服务地址、AI 配置、数据目录、环境变量收拢为更清晰的可配置入口，降低长期维护成本。

### 3. 用户投研流程入口

优先把真正高频的入口前置，例如：

- 自选
- 持仓
- 个股研究
- 复盘
- 研究沉淀

目标不是马上重写业务层，而是先让首页和导航更贴近用户日常使用路径。

### 4. 本地数据结构对齐

逐步把关注列表、持仓观点、研究沉淀接到用户自己的目录规范和存储约定上，但第一步以兼容为主，不做一次性全量替换。

## 第二阶段暂缓事项

以下事项在第二阶段不应过早推进：

- 底层数据抓取逻辑替换
- 前后端架构重构
- 大规模删模块
- 自动化编排和复杂工作流

原因是这些改动要么排错成本高，要么会把“系统可用性验证”和“长期产品优化”搅在一起。

## 风险与缓解

### 风险 1：首次接入时依赖较多，启动链路长

缓解：

- 保持上游目录结构和默认启动方式
- 优先验证前后端最小可运行路径
- 不在第一阶段混入裁剪和重构

### 风险 2：过早改动导致难以对照上游排错

缓解：

- 第一阶段以“完整镜像接入”为原则
- 保留与上游一致的目录和入口
- 第二阶段再做命名、配置和流程层改造

### 风险 3：用户自己的投研体系需求与上游默认路径不完全一致

缓解：

- 将第一阶段和第二阶段严格拆分
- 第二阶段优先改入口和配置，不急着改数据底层
- 先形成稳定可用的基础盘，再做深度定制

## 实施后的下一步

本设计确认后，下一步应进入实施计划阶段，而不是直接写代码。实施计划应覆盖：

1. 如何将上游仓库完整落地到当前目录
2. 如何验证前后端依赖与启动
3. 如何记录接入阶段的本地化差异
4. 如何为第二阶段的配置抽离留出最小改动点

## 结论

本次接入应采取“完整落地上游项目、先原样跑通、再逐步改造”的策略。对于当前空目录，这是风险最低、验证最快、后续演进空间最大的一条路径。
